# SESSION HANDOFF

## 1. Текущее состояние проекта

Выполнены Этапы 1–5 из `PLAN.md`.

- **Этап 1 — каркас:** Expo Router + TypeScript + React Native Paper, Safe Area, SQLite, локальные фото и общий фон `assets/backgrounds/gonext-bg.png`.
- **Этап 2 — навигация:** работают главный экран и маршруты «Места», «Поездки», «Следующее место», «Настройки». Экран `/next` пока остаётся заглушкой до Этапа 6.
- **Этап 3 — данные:** созданы типы `Place`, `Trip`, `TripPlace`; SQLite-схема и CRUD-репозитории; фото хранятся файлами, а в SQLite — только пути.
- **Этап 4 — «Места»:** список, поиск, фильтры, создание/редактирование, карточка, DD одной строкой, фото, карта и удаление. Этот этап визуально и функционально завершён.
- **Этап 5 — «Поездки»:** список поездок, создание/редактирование, даты, одна текущая поездка, выбор мест, маршрут, изменение порядка, посещение, дата визита, заметки, фото посещения и режимы «Все / План / Дневник».

Приложение рассчитано прежде всего на проверку в Expo Go на реальном Android. Экраны используют общий фиолетовый `#6750A4`, полупрозрачные белые карточки и MaterialCommunityIcons.

## 2. Последние изменения

Последние изменения относятся к экрану `app/trips/[id]/index.tsx`:

- кнопки экрана «Поездка» унифицированы по высоте, типографике, радиусу, границам и размеру иконок;
- общие параметры находятся в `src/theme/tripButtons.ts`:
  - высота `40`;
  - шрифт `14`, weight `500`;
  - иконка `18`;
  - `borderRadius: 4`;
  - outlined-граница `1.5`;
- наложение иконок на текст исправлено отдельным `tripButtonIconLabelStyle`: Paper MD3 использует отрицательный правый margin у контейнера иконки, поэтому для label с иконкой установлены `marginLeft: 24` и `marginRight: 16`; это даёт визуальный gap около `8 px` и центрирует группу «иконка + текст»;
- устаревшая ссылка на `primaryButtonStyle` в экране поездки удалена; используются `tripOutlineButtonStyle` / `tripFilledButtonStyle`. Если Expo показывает старую ошибку про `primaryButtonStyle`, это кеш Metro — исходный код ссылки уже не содержит, помогает запуск с очисткой кеша;
- заметки вынесены в `TripPlaceNotesSection`: чтение в карточке, добавление/редактирование в нижнем modal, подтверждение удаления; destructive-цвет используется только в подтверждающем Dialog;
- «Уже был» можно отменить, только если у `TripPlace` нет сохранённых заметок и фото; данные автоматически не удаляются;
- посещённые места нельзя переставлять стрелками;
- завершённой поездке кнопка «Сделать текущей» не показывается;
- в `handleSetCurrent` есть повторная защитная проверка, поэтому завершённую поездку нельзя назначить текущей прямым вызовом обработчика.

## 3. Что нельзя сломать

Нужно сохранить:

- создание и редактирование поездок;
- правило одной текущей поездки;
- добавление существующих `Place` в маршрут поездки;
- упорядоченный маршрут и перестановку непосещённых мест стрелками;
- `visited` / кнопку «Уже был» и возможность безопасно отменить случайное посещение;
- автоматическое заполнение и очистку `visitDate` через существующий репозиторий;
- заметки: просмотр, modal добавления/редактирования, удаление с подтверждением;
- фото посещения: галерея, камера, просмотр, удаление и файловое хранение;
- режимы «Все / План / Дневник»;
- открытие места на карте только по сохранённому `Place.dd`;
- текущий порядок блоков и согласованный UI экрана «Поездка»;
- завершённый UX экранов Этапа 4 «Места».

## 4. Важные технические решения

- **Текущая поездка:** хранится в `trips.current`. `setCurrentTrip(id)` выполняет транзакцию: сначала сбрасывает `current` у всех поездок, затем включает его у выбранной. `createTrip` и `updateTrip` при `current: true` также сбрасывают остальные поездки.
- **Завершённая поездка:** локальная функция `isTripEnded` в `app/trips/[id]/index.tsx` считает поездку завершённой, только если `endDate` строго раньше сегодняшней локальной календарной даты. В день окончания поездка ещё активна.
- **Сравнение дат:** без UTC и времени суток. Поддерживаются хранимый `YYYY-MM-DD` и UI-формат `DD.MM.YYYY`; сравниваются числовые ключи `YYYYMMDD`, составленные из локальной даты пользователя.
- **Формат дат:** UI использует `DD.MM.YYYY`, хранение — `YYYY-MM-DD`; преобразования находятся в `src/utils/dates.ts`.
- **Кнопки поездки:** использовать `src/theme/tripButtons.ts`, а не локальные дубли. Для кнопок с иконкой нужен `tripOutlineIconLabelStyle` / `tripFilledIconLabelStyle`; для кнопок без иконки — обычные label-стили.
- **TripPlace:** хранит `tripId`, ссылку `placeId`, `order`, `visited`, `visitDate`, `notes`, `photos`. Данные самого места не копируются; название и DD читаются из `Place`.
- **Порядок:** хранится как `trip_places.sort_order`, в TypeScript — `TripPlace.order`; `getTripPlacesByTripId` уже возвращает список по `sort_order`, а изменение выполняется только через `reorderTripPlaces`.
- **Посещение:** `visited` и `visitDate` хранятся в `trip_places`. `markTripPlaceVisited(true)` ставит дату, `false` очищает её.
- **Фото посещения:** файлы находятся в файловой системе приложения, таблица `trip_place_photos` хранит пути.

## 5. Что специально НЕ делать

Следующему Agent не нужно:

- переделывать завершённые Этапы 1–5;
- менять SQLite-схему, типы или архитектуру без необходимости для Этапа 6;
- менять дизайн существующих экранов;
- проводить общий рефакторинг проекта;
- переименовывать существующие сущности, поля или маршруты;
- менять бизнес-логику, не относящуюся к режиму «Следующее место»;
- начинать Этап 7 или последующие этапы.

## 6. Следующая задача

Следующая задача — **Этап 6 PLAN.md: режим «Следующее место»**.

Нужно:

1. получить поездку с `current = true` через существующий репозиторий;
2. найти первое место с `visited = false` по `TripPlace.order`;
3. реализовать экран `/next`;
4. показать название и краткую информацию о месте;
5. добавить действия:
   - «Открыть на карте»;
   - «Открыть в навигаторе» (Google Maps / системный);
6. обработать состояния:
   - текущей поездки нет;
   - все места текущей поездки уже посещены.

Для карты/навигатора использовать сохранённый `Place.dd`, не текущую геопозицию телефона. Этап 6 в этой сессии не реализовывался.
